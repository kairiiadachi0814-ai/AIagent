## 1. 目的

社内の決まりごとと過去の意思決定を**ハンドブック**（GitHub上のMarkdown文書群）として蓄積し、Chatwork上のAIエージェントがそれを参照して出典付きで回答できる状態を作る。
Phase 1 の目標は業務の自動化ではない。
「書いた量がそのままエージェントの賢さになる」体験を社内に作り、ハンドブックを書き残す習慣を定着させることである。

## 2. 用語

- **ハンドブック**：組織のルール、業務手順、過去の意思決定を書き溜めた正本。GitHubプライベートリポジトリの `handbook/` 以下に置く。
- **SOP（手順書）**：定型業務の段取りを1業務1ファイルで文書化したもの。`sops/` 以下に置く。Phase 1 では回答の参照元としてのみ使う。
- **エージェント**：Chatworkに常駐するAI。専用のChatworkアカウントとして振る舞う。

## 3. スコープ

Phase 1 で作るのは次の1機能である。

Chatworkの指定ルームでエージェント宛にメンションすると、ハンドブックとSOPを参照し、出典付きで回答を返す。

次はPhase 1 の対象外とする（Phase 2 以降）。

- カレンダー登録、タスク作成などの書き込み系操作
  **【変更（2026-08-17・版0.13）】社内ひな形からの書類作成（書類送付状・FAX送付状）をPhase 1 に前倒しで解禁した。**
  Phase 2 が課す「実行前に必ず人間の承認を挟む」は、次の3点で担保する。
  (1) 作るのは常に**下書き**で、依頼者本人のいるルームへ添付して返すだけ。宛先へ送る・提出する操作は一切しない
  (2) 依頼文に書かれていない宛先・書類名・部数を推測で埋めない。足りなければ作らずに聞き返す
  (3) 返信に「下書きです。日付・宛名・部数をご確認のうえ、印刷や送付はお手元でお願いします」を必ず添える
  契約書ひな形は対象外のまま（FR-08 参照）
- 定時配信（朝刊）
- ハンドブック更新の自動提案
- Google Drive、Box、Gmailの参照

## 4. システム構成

```
Chatwork（専用アカウント宛メンション）
  → Chatwork Webhook（自分宛メンション通知）
  → 受信サーバー（AWS Lambda または Cloud Run。Webhook署名を検証しキューに積む）
  → エージェント処理（Claude API を呼び出す）
      - ハンドブック／SOP を GitHub API 経由で取得して文脈に与える
      - 回答を生成する
  → Chatwork API で該当ルームへ返信
```

構成上の判断とその理由を記す。

- Chatwork連携の実装には、kubell社が公式提供するMCPサーバー（`@chatwork/mcp-server`、MITライセンス）を利用できる。運営元自身が保守しているため、API仕様への追従を自前で負わずに済む。
- ただしPhase 1 の返信は「メッセージ送信」1操作のみなので、MCPを使わずChatwork REST APIを直接叩く実装でもよい。どちらを採るかは実装時に決定し、本書の改版で記録する。
  **【決定（2026-08-13・版0.2）】REST API直接を採用。** 使用操作が送信・取得の2つのみで依存を最小化できるため。送信ロジックは `src/raizuinu/chatwork.py` に隔離済みで、将来MCPへ差し替える場合も同ファイルの変更で完結する。
- ハンドブックの取得は、リポジトリが小さいうちは全ファイル取得で足りる。肥大化したら検索（ファイル名・見出しインデックス）を導入する。

## 5. 機能要件

- **FR-01 メンション応答**：許可されたルームでエージェント宛のメンションを受けたら、そのメッセージと同一ルームの直近の会話（件数は設定値、初期値20件）を文脈として回答する。
- **FR-02 ハンドブック参照**：回答の前に必ずハンドブックとSOPを参照する。
- **FR-03 出典明記**：ハンドブックに基づく回答には、参照したファイル名と見出しを回答末尾に明記する。出典を捏造しない。
- **FR-04 不明の明示**：ハンドブックに書かれていないことは推測で埋めず、「ハンドブックに記載がない」と答える。あわせて、どのファイルに追記すべきかを提案してよい。
- **FR-05 ルーム制限**：応答するルームは許可リストで管理する。リスト外のルームからの呼び出しには応答しない。
- **FR-06 失敗時の通知**：処理が失敗した場合、無言で終わらせず「処理に失敗した」旨をルームに返す。詳細ログはサーバー側に残す。
- **FR-07 ひな形からの書類作成**（版0.13で追加）：書類送付状・FAX送付状の作成依頼を受けたら、社内ひな形に依頼内容を差し込んだ下書き（Word／Excel）を作り、Chatworkのルームへ添付して返す。使ったひな形の名称とBox URLを返信に必ず明記する（FR-03の出典明記と同趣旨）。ひな形の実体はリポジトリの `templates/` に白紙化して同梱する（VPSからBoxは参照できないため）。作れる書類は「送付状」「FAX送付状」の2種類。差出人となるグループ会社（社名・住所・TEL・FAX・部署・書式）は `templates/companies.json` の台帳で管理し、会社が増えても1件追加するだけで済ませる（ひな形は書式ごとに1つだけ持つ）。台帳にない会社名を差出人に指定された場合は、既定の会社で代用せず、必要な情報を聞き返す（別会社名義の書類が出来上がるのを防ぐため）。
- **FR-10 過去ログからの回答**（版0.15で追加）：ハンドブックに記載が無い質問（`has_answer=false`）については、質問が来たルームの過去ログを検索して答える。ChatworkのAPIが直近100件しか返さないため、5分ごとの巡回で発言を保存して積み上げる。同じ項目について複数の発言がある場合は**最新を正**とする（パスワードの変更など）。回答の末尾に、過去のやり取りを遡って答えている旨と、根拠にした発言の日付・発言者を必ず記載する。検索対象は質問が来たルームのみとし、ルームをまたいで参照しない。
- **FR-09 レターパック手配の取次ぎ**（版0.14で追加）：書類送付状を作ったら、その返信でレターパック手配の要否を確認する。必要と答えられたら枚数と種類（プラス／ライト）を受け取り、**投稿する文面をそのまま依頼者に見せて「送信」の返事を得てから**、備品・消耗品購入依頼チャットの総務担当者あてに投稿する。依頼文には使用会社名・宛先と使用内容・必要枚数・種類を載せ、誰の依頼でアシスタントが代理投稿しているかを明記する。総務からの返信は5分ごとの巡回で拾い、完了ならお礼を返して締め、質問なら依頼者へ取り次いでその答えを返す。投稿先ルームはメンションの許可ルーム（FR-05）に含めない——投稿と巡回にだけ使い、他部署のルームへ社内ナレッジが流れる経路を作らないため。
- **FR-11 FAX受信の見張り**（版0.16で追加）：FAX受信通知ルームを5分ごとに巡回し、通知ボットが流したPDFを読んで「どこから・何が届いたか」を担当者あてに知らせる。差出人は、通知の送信元番号を**FAX番号台帳（Googleスプレッドシート）**で照合したものを正とし、番号が無い・台帳に無い場合はPDFの記載から拾って根拠を明記する。発注書・注文書なら品名・数量・金額・納期を箇条書きでまとめ、それ以外（請求書・案内・広告など）は一行で種類だけ知らせる。担当者を To で呼び出すのは発注書・注文書・請求書・見積書・納品書のみ（`mention_kinds`）。案内・広告・その他は To を付けずにルームへ置くだけにし、営業FAXや迷惑FAXで通知が鳴らないようにする。FAXは紙を逆さまに入れて送られてくることがあるため、逆さま・判読不能と判定されたら回転してもう一度だけ読む（実例 2026-09-05: 逆さまの発注書が「その他」と判定された）。それでも読めなかった場合は種類を決めつけず、担当者を To で呼んで「読み取れなかった」と知らせる（FR-06と同趣旨。読めないFAXは発注書かもしれないので静かに置かない）。数量・金額は読み取りであり原本で確認する旨を毎回添える。1日の処理数に上限を設け、迷惑FAXで費用が青天井にならないようにする。通知ルームは許可ルーム（FR-05）に含めない。台帳に取引先を足すときはスプレッドシートに1行追加するだけでよい。知らせる時間帯は月〜金の 8:30〜19:30（版0.17）。土日は知らせず、時間外に届いた分は控えておいて次の時間帯の頭に知らせる。祝日は平日と同じに扱う。発注書・注文書は通知の末尾で「対応完了」の返し方を示し、その返事が無ければ翌営業日 9:00 に確認と対応が済んだかを聞き、それにも返事が無ければ 12:00 に確認漏れがないかをもう一度だけ聞いて打ち切る（以後は人に任せる）。返事は通知への返信でなくても、担当者が「完了」「済」と書けば済んだと読み、「未対応」「対応中」は済んだと読まない。完了の報告には「対応ありがとうございます」等の一言を、その報告への返信で返す（黙って閉じない。人の会話として不自然にならないため）。通知先は導入テスト中（版0.17時点）は篠田・足立の2名、テスト完了後に篠田・福本・中浦・札葉の4名へ切り替える。
- **FR-12 予定の照会・登録と日程調整**（版0.18で記載。照会・登録・朝の通知は2026-08-14実装）：(1) 照会——「足立さんの今日の予定は？」に、トヨクモ スケジューラー（iCal出力）とGoogleカレンダーを束ねて答える。部署の誰でも聞ける。(2) 登録・取り消し——管理者だけが行える。登録先はGoogleカレンダー（トヨクモは外部から書けないため）。登録した内容を必ず復唱し、直前の1件は「取り消して」で消せる。(3) 朝の通知——毎朝1回、その日の予定を部署ルームへ投稿する（土日は除く）。(4) 空き時間の提案（版0.18で追加）——「篠田さんと来週1時間打合せしたい、いつがいい？」に、関係者全員（依頼者を含む）の予定と勤務日・勤務時間を突き合わせ、全員が空いている枠を3件まで候補で返す。営業時間・昼休み・予定の前後の余白・祝日は設定値。候補の日時はプログラムが決め、モデルには依頼文の読み取り（相手・所要時間・期間・午前午後の希望）だけを任せる。他のメンバーの予定は各自のトヨクモのiCal出力（環境変数）か共有されたGoogleカレンダーから読み、未設定の人は勤務日だけで見てその旨を返信に明記する。読めなかったカレンダーがあればそれも明記する。(5) 候補からの登録——管理者は「1番で登録して」で候補をそのまま登録できる（候補は24時間だけ覚える）。(6) 登録前の確認——日時を決めて登録を頼まれ、相手の名前が出ていれば、その人の予定と重ならないかを先に確かめ、重なっていれば登録せず理由と代わりの候補を返す。既存の予定を動かす提案はしない。
- **FR-08 契約書ひな形の除外**（版0.13で追加）：契約書・覚書・誓約書などのひな形は差し込み生成の対象外とし、ひな形リンク集のURL案内に倒す。締結前にLegalForceでのリーガルチェックが必須であり、条項の当てはめを機械的に行うべきではないため。

## 6. 非機能要件

- **NFR-01 認証情報の管理**：Chatwork APIトークン、GitHubトークン、Claude APIキーはSecrets Manager等で管理し、コードやリポジトリに直書きしない。
- **NFR-02 最小権限**：GitHubトークンはハンドブックリポジトリの読み取りのみ。Chatworkトークンはメッセージ送受信と、許可ルームへのファイルアップロードに必要な範囲のみ（版0.13でFR-07のためアップロードを追加。Chatwork APIトークンは機能を絞れない方式のため、アップロード先は許可ルーム判定〔FR-05〕を通ったルームに限られることをコード側で担保する）。
- **NFR-03 監査ログ**：いつ、誰の依頼で、何を参照し、何を返したかを記録する。保存期間は運用開始時に定める。
- **NFR-04 コスト上限**：Claude APIの月次利用額に上限とアラート（例：上限の70%到達で通知）を設定する。上限到達時はエージェントが停止する仕様とし、停止した旨を管理者に通知する。みらいいぬはトークン上限到達で無言停止する事故を経験しており、停止の検知と通知を最初から組み込む。
- **NFR-05 応答時間**：メンションから初回応答まで数十秒を許容する。長考が必要な場合は「調べています」と先に返してよい。

## 7. ガードレール（設計原則）

みらいいぬの公開情報から採用する原則を明文化する。

1. 出典をごまかさない。出典が特定できない情報は回答に含めない。
2. 書かれていないことは「分からない」と正直に答える。滑らかに言い切れることを品質と見なさない。
3. 一時的な検討中の内容をハンドブック（正本）に書かない。正本には確定した決定だけを載せる。
4. 権限とデータの境界はエージェントの賢さと無関係に人間が決める。Phase 1 の書き込みは、(a) 依頼者自身のいる許可ルームへ下書きを添付すること（版0.13）と、(b) レターパックの手配依頼を社内の指定ルームへ投稿すること（版0.14。投稿する文面を依頼者に見せ、「送信」の返事を得てから投稿する）に限る。社外への送付・提出・登録は一切しない。
6. 保存するのは業務に必要な範囲だけ。チャットの過去ログは、応答するルーム（`chat_archive.room_ids`）の発言者・本文・日時のみをVPS内に保存し、保存期間を過ぎたものは自動で消す（版0.15。既定730日）。検索は質問が来たルーム内に限り、ルームをまたいで参照しない。過去ログから答えた場合はその旨を返信に明記する。回答本文は監査ログへ書かない。
5. 間違えたら認めて直す。誤答の指摘はハンドブックの改善（追記・修正）につなげる。
